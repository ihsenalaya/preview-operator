2.5 experiments.md
----------------------------------------------------

Create a fault injection experiment matrix.

Include at least these scenarios:

F1 Invalid SQL migration
- root cause: migration syntax or semantic error
- expected evidence: migration Job failed, SQL error log, changed migration file

F2 Missing environment variable
- root cause: ConfigMap/Secret/env var removed or renamed
- expected evidence: CrashLoopBackOff, pod logs, deployment env diff

F3 Invalid container image tag
- root cause: non-existing image
- expected evidence: ImagePullBackOff, Kubernetes event, image field

F4 Removed or broken API endpoint
- root cause: backend incompatible API change
- expected evidence: contract test failure, changed backend route/controller file

F5 Frontend breaking change
- root cause: UI selector or route changed
- expected evidence: E2E test failure, frontend diff, browser test log

F6 Database readiness timeout
- root cause: app starts before DB ready or readiness too slow
- expected evidence: readiness/liveness events, app timeout logs, DB pod status

F7 Broken Service selector
- root cause: Service selector does not match pods
- expected evidence: Service has no endpoints, E2E timeout, service manifest diff

F8 Artificial latency / timeout
- root cause: slow backend or network delay
- expected evidence: long OTel trace span, timeout log, failed E2E test

F9 Incorrect seed data
- root cause: required test data missing or malformed
- expected evidence: seed job logs, regression failure, missing DB record

F10 Flaky test
- root cause: non-deterministic test behavior
- expected evidence: intermittent failure pattern, no stable infrastructure cause

For each scenario include:
- injected change
- expected failed test suite
- expected Kubernetes signal
- expected log evidence
- expected trace evidence if applicable
- expected diagnosis
- ground truth
- success criterion

Also define repetitions:
- Run each scenario at least 10 times
- Run parallel previews with 1, 5 and 10 concurrent PRs if feasible
- Compare Kind vs AKS if AKS is available

2.8 threats-to-validity.md
----------------------------------------------------

Include:

Internal validity:
- injected failures may not represent all real failures
- diagnostic scoring may be subjective
- traces may not always be available

External validity:
- demo app may be simpler than production systems
- results from Kind may differ from managed Kubernetes
- one operator implementation may not generalize to all platforms

Construct validity:
- RCA accuracy is difficult to measure
- hallucination rate requires careful annotation
- evidence relevance may be subjective

Conclusion validity:
- number of runs may be small
- flaky tests may affect results
- LLM behavior may change depending on model/version

Mitigations:
- deterministic fault injection
- known ground truth
- repeated runs
- independent scoring rubric
- report confidence intervals where possible
- separate Kind and AKS results
